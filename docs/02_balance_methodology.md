# Era of Strife — Методология анализа баланса

## 1. Назначение документа

Этот документ описывает методологию анализа баланса, используемую в проекте **Era of Strife**.

В проекте применяется data-driven подход: исходные Game Design-решения преобразуются в структурированные числовые параметры, после чего проверяются с помощью Python, combat simulation и сравнительного анализа.

Основной рабочий процесс выглядит следующим образом:

**Game Design → Structured Data → Validation → Simulation → Analysis → Balance Hypothesis → Iteration → Re-test**

Цель анализа заключается не в том, чтобы сделать всех юнитов численно одинаковыми.

Методология предназначена для того, чтобы:

- находить числовые выбросы;
- обнаруживать потенциально проблемные matchup;
- проверять Balance Hypotheses;
- измерять последствия изменений;
- разделять direct и indirect effects;
- исследовать чувствительность результата к отдельным параметрам;
- находить threshold values;
- сохранять Faction Identity и Unit Identity;
- обеспечивать воспроизводимость результатов;
- принимать решения по балансу на основании данных.

---

# 2. Структура данных

Проект разделяет исходные данные и результаты анализа.

Основные характеристики юнитов хранятся в:

`data/unit_balance.csv`

Дополнительные CSV-файлы содержат информацию о:

- способностях;
- Balance Risks;
- Interaction Matrix;
- Combat Scenarios;
- Balance Tests.

Python-скрипты считывают исходные данные и сохраняют результаты анализа отдельно в:

`analysis/results/`

Экспериментальные результаты не должны автоматически перезаписывать исходный `unit_balance.csv`.

Такое разделение необходимо для:

- сохранения baseline;
- воспроизводимости экспериментов;
- сравнения Before/After;
- диагностики ошибок;
- возможности отката;
- прозрачности Balance Iterations.

# 3. Unit Balance Parameters

Каждый юнит представлен набором числовых и категориальных параметров.

В зависимости от конкретного этапа анализа используются такие характеристики, как:

- HP;
- Damage;
- Attack Speed;
- Attack Interval;
- DPS;
- Attack Range;
- Move Speed;
- Role;
- Faction;
- Attack Type.

Эти параметры позволяют переводить качественные Game Design-решения в измеримые значения.

Например, Design Intent:

> Stone Ogre должен быть тяжёлым и очень устойчивым Tank.

может быть связан с измеряемыми параметрами:

- HP;
- Damage;
- DPS;
- Combat Time;
- Remaining HP;
- количеством атак;
- результатами matchup.

Таким образом можно сравнивать:

**Intended Design**

и

**Observed Numerical Behavior**.

---

# 4. Базовые и производные характеристики

Не все используемые метрики являются непосредственно исходными характеристиками.

Часть значений рассчитывается на основании других параметров.

## 4.1. Damage

`Damage` показывает количество Damage, наносимого одной базовой атакой.

Сам по себе Damage не позволяет полностью оценить offensive power юнита.

Юнит с большим Damage, но медленными атаками может иметь меньший DPS, чем юнит с меньшим Damage, но высокой частотой атак.

---

## 4.2. Attack Speed и Attack Interval

Необходимо различать:

**Attack Speed**

и

**Attack Interval**.

Attack Speed характеризует частоту атак.

Attack Interval показывает промежуток времени между атаками.

Чем меньше Attack Interval, тем чаще юнит способен атаковать.

В combat simulation особенно важно использовать единое определение этих параметров, чтобы избежать двойного учёта скорости атаки.

---

# 5. DPS

**DPS — Damage Per Second**

DPS используется для приблизительной оценки sustained offensive power юнита.

В зависимости от структуры данных он может быть рассчитан через Damage и скорость выполнения атак.

Если используется Attack Speed:

**DPS = Damage × Attack Speed**

Если используется Attack Interval:

**DPS = Damage / Attack Interval**

Например:

если:

**Damage = 96**

и:

**Attack Interval = 1.6 sec**

то:

**DPS = 96 / 1.6 = 60**

Именно поэтому первоначальное значение Stone Ogre:

**Damage = 96**

соответствовало:

**DPS = 60**

при используемом Attack Interval.

DPS позволяет сравнивать sustained Damage разных юнитов более корректно, чем один Damage.

---

# 6. Combat Time

`Combat Time` показывает продолжительность simulated matchup.

Эта метрика полезна даже в тех случаях, когда победитель не изменился.

Например:

**Before**

Stone Ogre побеждает за 10 sec.

**After**

Stone Ogre побеждает за 14 sec.

Формально Winner остался прежним.

Однако offensive efficiency Stone Ogre уменьшилась.

Поэтому анализировать только Win/Loss недостаточно.

Combat Time помогает обнаруживать изменения, которые не пересекают границу смены Winner.

---

# 7. Remaining HP

`Remaining HP` показывает количество HP, оставшееся у победителя после окончания matchup.

Рассмотрим два результата.

### Matchup A

Winner:

**Stone Ogre**

Remaining HP:

**5%**

### Matchup B

Winner:

**Stone Ogre**

Remaining HP:

**80%**

В обоих случаях результат:

**Stone Ogre Win**

Однако степень доминирования сильно различается.

Поэтому Remaining HP позволяет оценить, насколько близким был matchup.

---

# 8. Количество уникальных matchup

В проекте присутствуют:

**12 юнитов**

Для базового анализа каждый юнит сравнивается с каждым другим юнитом один раз.

Количество уникальных неупорядоченных пар определяется сочетанием:

**C(n, 2)**

Формула:

**C(n, 2) = n × (n - 1) / 2**

Для 12 юнитов:

**C(12, 2) = 12 × 11 / 2**

**C(12, 2) = 66**

Таким образом, один полный pairwise analysis содержит:

**66 уникальных matchup**

Пары:

`Unit A vs Unit B`

и:

`Unit B vs Unit A`

не считаются двумя отдельными matchup в тех экспериментах, где порядок участников не изменяет саму исследуемую пару.

---

# 9. Результат matchup

В базовой combat simulation возможны три основных результата:

- Win;
- Loss;
- Draw.

При сравнении Balance Iterations дополнительно определяется, изменился ли результат matchup.

Например:

### Пример 1

Before:

**Unit A Win**

After:

**Unit A Win**

Результат сравнения:

**Unchanged**

### Пример 2

Before:

**Unit A Win**

After:

**Draw**

Результат сравнения:

**Changed**

### Пример 3

Before:

**Unit A Win**

After:

**Unit B Win**

Результат сравнения:

**Changed**

Такой подход позволяет определить, насколько широко конкретное изменение параметров распространилось по matchup matrix.

---

# 10. Unit-Level Analysis

Результаты отдельных matchup агрегируются для анализа каждого юнита.

На разных этапах проекта используются показатели:

- Wins;
- Losses;
- Draws;
- Win Rate;
- Combat Score;
- Distance From 50;
- изменение показателей между Balance Iterations.

Эти метрики помогают обнаруживать потенциальные числовые выбросы.

Однако они не используются как автоматическое доказательство того, что юнит является OP или слишком слабым.

Дополнительно учитываются:

- Role;
- Unit Identity;
- Faction Identity;
- intended counters;
- способности;
- взаимодействия;
- Balance Risks.

---

# 11. Reference Point 50%

В проекте используется значение:

**50%**

как аналитический reference point.

Для значения `W` расстояние от 50% можно определить как:

**Distance From 50 = |W - 50|**

Например:

если:

**W = 70%**

то:

**|70 - 50| = 20 percentage points**

Если:

**W = 35%**

то:

**|35 - 50| = 15 percentage points**

Чем больше Distance From 50, тем сильнее значение отклоняется от центрального reference point.

---

# 12. Почему 50% не является обязательной целью

Era of Strife строится на асимметричных фракциях и разных ролях.

Поэтому проект **не предполагает**, что каждый юнит обязан иметь:

**Win Rate = 50%**

или:

**Combat Score = 50**

против всех возможных противников.

В RTS могут существовать:

- hard counters;
- soft counters;
- favorable matchup;
- unfavorable matchup;
- специализированные юниты;
- разные роли;
- Faction Identity.

Поэтому Distance From 50 используется как диагностическая метрика, а не как абсолютная цель баланса.

---

# 13. Average Distance From 50

Для оценки общей числовой картины используется среднее отклонение от 50%.

Упрощённая формула:

**Average Distance From 50 = Σ|Wᵢ - 50| / N**

где:

- `Wᵢ` — показатель отдельного юнита;
- `N` — количество анализируемых юнитов.

Эта метрика помогает ответить на вопрос:

> уменьшились ли общие числовые крайности после Balance Iteration?

Но использовать её отдельно нельзя.

Например, Average Distance может улучшиться, хотя конкретный важный matchup стал хуже.

Возможна и обратная ситуация:

Average Distance не изменился, но проблемный direct matchup улучшился.

---

# 14. Baseline

Перед внесением Balance Changes необходимо иметь исходное состояние системы.

Оно называется:

**baseline**

Baseline используется как контрольная точка.

С ним сравниваются последующие Balance Iterations.

Без baseline невозможно корректно ответить на вопрос:

> Что именно изменилось после корректировки параметров?

Поэтому исходные данные сохраняются отдельно и не перезаписываются экспериментальными значениями.

---

# 15. Balance Hypothesis

Balance Change должен начинаться не со случайного изменения цифры, а с гипотезы.

Плохой подход:

> Stone Ogre сильный, уменьшим что-нибудь.

Более правильная формулировка:

> Stone Ogre создаёт слишком высокое offensive pressure относительно своей роли Heavy Frontline Tank. Снижение Damage может уменьшить offensive power, сохранив высокую Durability.

Такое утверждение можно проверить.

Рабочая последовательность:

1. обнаружить потенциальную проблему;
2. определить, какая характеристика может быть её причиной;
3. сформулировать Balance Hypothesis;
4. выбрать ограниченное изменение;
5. выполнить simulation;
6. сравнить Before/After;
7. проанализировать direct effects;
8. проверить indirect effects;
9. принять или отклонить гипотезу.

---

# 16. Controlled Parameter Changes

При возможности в одной Balance Iteration изменяется минимальное количество параметров.

Основной принцип:

> Change as few variables as necessary.

Если одновременно изменить:

- HP;
- Damage;
- Attack Speed;
- Attack Range;
- Move Speed;
- Ability Cooldown;

то после simulation будет сложно определить, какая именно характеристика стала причиной результата.

Если изменяется только:

**Damage**

то причинная связь становится значительно понятнее.

Этот подход особенно важен при анализе Stone Ogre.

---

# 17. Direct Target

`Direct Target` — юнит, характеристика которого намеренно изменяется в конкретной Balance Iteration.

Например:

если в Iteration изменяется:

**Stone Ogre Damage**

то:

`HOR_02 — Stone Ogre`

является:

**Direct Target**

Это понятие необходимо сохранять на всех последующих этапах анализа.

---

# 18. Direct Effect

Если результат изменившегося matchup включает Direct Target, изменение классифицируется как непосредственно связанное с Balance Iteration.

Например:

`Great Forest Bear vs Stone Ogre`

Если Stone Ogre является Direct Target и после изменения его Damage результат matchup меняется:

**Stone Ogre Win → Draw**

такой эффект относится к:

**Direct Effect**

---

# 19. Indirect Effect

Если matchup изменился, хотя ни один из его участников не является Direct Target, такой результат требует отдельного анализа.

Он классифицируется как:

**Indirect Effect**

Indirect Effects особенно важны, поскольку могут указывать на:

- hidden coupling;
- системную зависимость;
- ошибку аналитического pipeline;
- unintended side effect;
- изменение связанных данных.

Indirect Effect не считается автоматически плохим.

Сначала необходимо определить его причину.

---

# 20. Side Effects

`Side Effect` — непредусмотренное следствие Balance Change, которое требует дополнительной проверки.

Например, если изменяется только Stone Ogre, но неожиданно меняется matchup между двумя Elves, это является основанием для диагностики.

Возможные причины:

- общая зависимость в коде;
- изменение исходных данных;
- неправильная классификация;
- ошибка aggregation;
- действительно существующая системная зависимость.

Поэтому Side Effects нельзя просто игнорировать.

---

# 21. Combat Simulation

В проекте используется упрощённая deterministic combat simulation.

Основная задача simulation — не полностью воспроизвести RTS, а создать контролируемую среду для сравнения числовых характеристик.

Базовая модель позволяет получать:

- Winner;
- Combat Time;
- Remaining HP;
- количество атак;
- matchup result.

При одинаковых входных данных deterministic simulation должна выдавать одинаковый результат.

---

# 22. Логика базовой 1v1 simulation

В текущей базовой модели основными параметрами являются:

- HP;
- Damage;
- Attack Interval.

Для каждого юнита отслеживается время следующей атаки.

Когда наступает момент атаки, противнику наносится соответствующий Damage.

Если оба юнита должны атаковать в один и тот же момент времени, обе атаки могут быть обработаны в рамках одного временного события.

Это позволяет корректно получать:

**Draw**

при взаимном уничтожении.

Simulation продолжается до тех пор, пока:

- один юнит не потеряет весь HP;
- оба юнита не потеряют весь HP одновременно;
- не будет достигнуто другое условие завершения конкретного теста.

---

# 23. Почему используется deterministic simulation

Deterministic model полезна на раннем этапе Balance Analysis, потому что она устраняет случайность.

Если:

- исходные параметры одинаковы;
- логика simulation одинакова;

результат должен быть одинаковым.

Это позволяет связать изменение результата с изменением параметров, а не со случайным RNG.

Позже модель можно расширить stochastic-механиками.

---

# 24. Ограничения combat simulation

Текущая базовая simulation не является полной моделью реального RTS-боя.

Она пока не моделирует полностью:

- способности;
- Attack Range;
- Move Speed;
- Positioning;
- Pathfinding;
- Terrain;
- Target Selection;
- Army Composition;
- Focus Fire;
- Economy;
- Production;
- Player Skill;
- Human Reaction;
- Network Latency.

Поэтому результаты следует интерпретировать как:

**controlled numerical evidence**

а не как:

**реальный прогноз PvP Win Rate**.

---

# 25. Reproducibility

`Reproducibility` означает возможность повторить эксперимент при одинаковых условиях и получить тот же результат.

Для Iteration 01 combat simulation была повторена:

**5 раз**

В каждом запуске проверялось:

**66 matchup**

Следовательно, суммарно в рамках проверки было обработано:

**66 × 5 = 330 matchup records**

Важно:

это не 330 уникальных matchup.

Это:

**66 одинаковых уникальных пар, повторённых 5 раз.**

---

# 26. Результат Reproducibility Check

Проверка Iteration 01 показала:

| Metric | Result |
|---|---|
| Runs | 5 |
| Matchups Per Run | 66 |
| Byte Identical Files | Yes |
| Unstable Matchups | 0 |
| Changed Row Comparisons | 0 |
| Changed Field Comparisons | 0 |
| Reproducibility Status | Reproducible |

Это означает, что повторные запуски при одинаковых условиях дали одинаковые результаты.

---

# 27. Reproducibility не означает Correctness

Это одно из важных методологических различий проекта.

Simulation может быть:

**Reproducible**

но при этом содержать ошибку.

Например, если в deterministic-коде используется неправильная формула, скрипт может пять раз подряд идеально воспроизвести один и тот же неправильный результат.

Поэтому:

**Reproducibility = стабильность результата**

но не обязательно:

**Reproducibility = правильность результата**

Для проверки корректности дополнительно используются:

- diagnostics;
- sanity checks;
- comparison;
- data lineage analysis;
- sensitivity analysis.

---

# 28. Data Lineage

`Data Lineage` описывает происхождение данных и их движение между этапами analytical pipeline.

Для Balance Analysis важно знать:

- откуда получено исходное значение;
- какой файл является baseline;
- какая Iteration изменила параметр;
- какой юнит являлся Direct Target;
- какой скрипт создал результат;
- какой результат относится к какой версии.

Потеря этой информации может привести к неправильной интерпретации даже при корректных математических расчётах.

---

# 29. Диагностика Iteration 01

Во время анализа Iteration 01 была обнаружена проблема классификации.

Balance Iteration содержала два Direct Targets:

- `HOR_01`
- `HOR_02`

Однако один из downstream-этапов первоначально показывал:

**Direct Target Units = 0**

Это противоречило исходным данным Iteration.

Проблема потребовала отдельной диагностики.

---

# 30. Причина диагностической проблемы

Combat simulation сама по себе не являлась основной причиной ошибки.

Проблема заключалась в том, что downstream impact analysis не использовал корректный источник данных для определения Direct Targets.

В результате информация о том, какие юниты были изменены намеренно, могла потеряться.

После диагностики source of truth для Direct Target classification был скорректирован.

Это стало практическим примером важности Data Lineage.

---

# 31. Sensitivity Analysis

`Sensitivity Analysis` используется для исследования того, насколько результат чувствителен к изменению конкретного параметра.

Основной вопрос:

> Что происходит с результатом, если постепенно изменять один параметр, сохраняя остальные условия постоянными?

Например, для Stone Ogre можно изменять HP по диапазону значений и для каждого значения выполнять одинаковые matchup.

---

# 32. Что фиксируется при Sensitivity Analysis

Для каждого tested value можно сохранять:

- Tested HP;
- Opponent;
- Opponent Role;
- Winner;
- Result;
- Combat Time;
- Ogre Remaining HP;
- Opponent Remaining HP;
- Ogre Attacks;
- Opponent Attacks.

Это позволяет увидеть не только смену Winner, но и постепенное изменение характера боя.

---

# 33. Зачем нужен Sensitivity Analysis

Одна выбранная цифра не показывает устойчивость результата.

Например:

если при:

**HP = 1760**

Stone Ogre выигрывает,

это ещё не говорит, насколько стабильна эта победа.

Если при:

**HP = 1759**

результат уже Draw,

то matchup находится непосредственно около threshold.

Если же Stone Ogre продолжает выигрывать даже при значительном снижении HP, результат намного устойчивее.

---

# 34. Threshold

`Threshold` — область параметра, около которой качественный результат matchup изменяется.

Например:

**HP = X + 10 → Win**

**HP = X → Draw**

**HP = X - 10 → Loss**

В таком случае значение около `X` является важной transition area.

Threshold Analysis позволяет исследовать её подробнее.

---

# 35. Threshold Refinement

После широкого Sensitivity Analysis можно уменьшить шаг изменения параметра около интересующей области.

Например, сначала:

**100 HP step**

затем:

**25 HP step**

а около transition:

**5 HP step**

или меньше.

Такой подход эффективнее, чем сразу тестировать весь огромный диапазон с очень маленьким шагом.

---

# 36. Почему возникают thresholds

Combat simulation работает с дискретными атаками.

Юнит не наносит бесконечно малый Damage каждую долю секунды.

Он выполняет отдельные атаки.

Поэтому небольшое изменение HP может позволить пережить ещё одну атаку.

А это, в свою очередь, может позволить выполнить собственную дополнительную атаку.

В результате небольшое изменение параметра способно привести к:

**Win → Draw**

или:

**Draw → Loss**

Поэтому эффект Balance Change не всегда является линейным.

---

# 37. Sensitivity Analysis и Balance Iteration — не одно и то же

Эти процессы выполняют разные задачи.

## Sensitivity Analysis

Вопрос:

> Как система реагирует на разные значения параметра?

Исследуется диапазон.

## Balance Iteration

Вопрос:

> Что произойдёт, если принять конкретное значение как Balance Candidate?

Проверяется конкретная гипотеза.

Таким образом:

**Sensitivity Analysis помогает выбрать и понять Balance Candidate.**

---

# 38. Stone Ogre как пример выбора Balance Lever

Stone Ogre имеет Design Identity:

**Heavy Frontline Tank**

Его сильная сторона:

**Very High Durability**

Если проблема заключается в том, что Stone Ogre слишком силён, можно рассмотреть несколько Balance Levers:

- HP;
- Damage;
- DPS;
- Attack Interval;
- Stone Skin Damage Reduction;
- Stone Skin Duration;
- Cooldown.

Однако снижение HP напрямую ослабляет ключевую идентичность юнита.

Поэтому в проведённых Balance Iterations основной акцент был сделан на:

**Damage**

Цель:

> уменьшить offensive pressure, сохранив Durability.

---

# 39. Before/After Comparison

Каждая Balance Iteration сравнивается с предыдущим состоянием.

Для каждого параметра можно хранить:

- Before;
- After;
- Absolute Change;
- Percentage Change.

Например:

Stone Ogre Damage:

**Before = 96**

**After = 91.2**

Absolute Change:

**91.2 - 96 = -4.8**

Percentage Change:

**(-4.8 / 96) × 100 = -5%**

Такая структура делает Balance Change прозрачным.

---

# 40. Matchup Comparison

После Balance Change выполняется тот же набор matchup.

Для каждой пары сравниваются:

- Winner Before;
- Winner After;
- Result Before;
- Result After;
- Combat Time Before;
- Combat Time After;
- Remaining HP;
- другие доступные показатели.

После этого matchup классифицируется как:

**Changed**

или:

**Unchanged**

---

# 41. Changed Matchup Share

Если из 66 matchup изменились 3:

**3 / 66 × 100 ≈ 4.55%**

Следовательно, изменилось приблизительно:

**4.55% matchup matrix**

Но эта цифра сама по себе не говорит, является ли Iteration хорошей.

Нужно дополнительно определить:

- какие matchup изменились;
- содержат ли они Direct Targets;
- были ли изменения ожидаемыми;
- появились ли Side Effects;
- сохранилась ли Unit Identity.

---

# 42. Почему меньше Changed Matchups не всегда лучше

Можно предположить:

> чем меньше matchup изменилось, тем лучше Balance Change.

Это не всегда верно.

Если Balance Change должен исправить пять проблемных matchup, но изменился только один, изменение может быть слишком слабым.

С другой стороны, если небольшая корректировка одного юнита неожиданно меняет половину matchup matrix, это может указывать на слишком сильное системное воздействие.

Поэтому количество Changed Matchups необходимо оценивать относительно исходной Balance Hypothesis.

---

# 43. Unit Improvement Classification

На уровне юнитов результаты Before/After могут классифицироваться как:

- Improved;
- Worsened;
- Unchanged.

Классификация основывается на выбранной аналитической метрике.

При этом термин:

**Improved**

не означает автоматически:

> этот юнит стал лучше с точки зрения всего Game Design.

Он означает, что показатель улучшился согласно конкретному используемому критерию.

Поэтому числовая классификация всегда должна сопровождаться Design Interpretation.

---

# 44. Local Metrics и Global Metrics

Проект разделяет локальные и глобальные показатели.

### Local Metric

Описывает конкретный юнит или matchup.

Например:

- Stone Ogre Combat Score;
- Great Forest Bear vs Stone Ogre result;
- Stone Ogre Remaining HP.

### Global Metric

Описывает систему в целом.

Например:

**Average Distance From 50**

Эти метрики могут двигаться в разных направлениях.

---

# 45. Почему Local Improvement может не изменить Global Metric

Предположим, изменяется только один юнит из двенадцати.

Его показатель заметно улучшается.

Но показатели остальных одиннадцати юнитов остаются прежними или часть из них изменяется в противоположном направлении.

В таком случае Average Distance может практически не измениться.

Это не означает, что Balance Change не сработал.

Это означает, что его воздействие было локальным.

---

# 46. Source Data Integrity

Исходный файл:

`data/unit_balance.csv`

не должен незаметно изменяться в ходе экспериментов.

Поэтому Balance Iterations создают отдельные результаты.

На важных этапах дополнительно проверяется целостность source data.

Один из используемых методов:

**SHA-256 hash**

Если hash Before и After совпадает, содержимое исходного файла не изменилось.

---

# 47. Почему Source Integrity важна

Если эксперимент автоматически изменяет baseline, возникают проблемы:

- невозможно точно восстановить Before;
- сложнее сравнивать Iterations;
- повышается риск накопления ошибок;
- становится сложнее воспроизводить эксперимент;
- теряется история решений.

Поэтому проект разделяет:

**Source Data**

**Experimental State**

**Generated Results**

---

# 48. Iteration Comparison

После выполнения нескольких Balance Iterations необходимо сравнивать не только каждую Iteration с baseline, но и Iterations между собой.

Например:

**Iteration 01 vs Iteration 02**

Сравнение может включать:

- Direct Targets;
- Parameter Changes;
- Improved Units;
- Worsened Units;
- Unchanged Units;
- Changed Matchups;
- Direct Effects;
- Indirect Effects;
- Average Distance From 50;
- итоговую классификацию.

Это позволяет понять, становится ли следующая Iteration более точной и контролируемой.

---

# 49. Decision Framework

Balance Candidate оценивается по нескольким вопросам.

### 1. Изменился ли Direct Target?

Если изменяемый параметр практически не повлиял на юнит, Balance Change может быть слишком слабым или не связанным с проблемой.

### 2. Улучшилась ли исходная проблема?

Сам факт изменения цифры не означает успех.

Необходимо проверить Balance Hypothesis.

### 3. Какие matchup изменились?

Важно определить, были ли они связаны с Direct Target.

### 4. Появились ли Indirect Effects?

Unexpected Effects требуют диагностики.

### 5. Сохранилась ли Unit Identity?

Нельзя считать Tank успешно сбалансированным только потому, что он перестал быть Tank.

### 6. Что произошло с Global Metrics?

Они дают дополнительный контекст.

### 7. Воспроизводится ли результат?

Одинаковые условия должны давать одинаковый результат в deterministic model.

Python не должен самостоятельно принимать финальное Game Design-решение только на основании одной формулы.

Python используется для:

- расчётов;
- поиска аномалий;
- simulation;
- comparison;
- автоматизации;
- проверки гипотез.

Финальная интерпретация требует учитывать:

- Faction Identity;

- ограничения модели.

Таким образом:

**Data informs the decision.**

Но:

**Data does not replace Game Design.**

# 54. Главный принцип методологии

Основной принцип проекта можно сформулировать следующим образом:

> Balance Change — это проверяемая гипотеза, а не случайное изменение числа.

Каждое значимое изменение должно иметь:

- причину;
- Direct Target;
- Balance Lever;
- Before;
- After;
- ожидаемый эффект;
- измеримый результат;
- анализ Side Effects;
- итоговую интерпретацию.

Такой подход позволяет превратить балансировку из процесса:

**«изменить цифры и посмотреть»**

в процесс:

**«сформулировать гипотезу → провести контролируемый эксперимент → измерить результат → принять следующее решение».**
